# 取得失敗で画面を落とさない／往復の削減

ブランチ: `fix/resilient-and-faster-pages`

## 何が起きていたか

タスク画面と予定画面が開けなくなった。

第 2 期で `tasks` の取得に `assignee_member_id` と `project_members(name)` の
結合を加えたが、**移行 SQL が未適用だと問い合わせ自体が失敗する。**
予定画面もタスク一覧を読むため、両方が同時に落ちた。

`.catch` は名簿の読み取りにしか掛かっておらず、タスク取得の失敗は捕まえていなかった。

## 直したこと

### 取得の失敗で画面ごと落とさない

`lib/domain/load-result.ts` の `attempt` で取得を包み、
失敗した箇所だけを `LoadError` で知らせて残りは出す。

真っ白な画面では、故障なのか権限なのか、何も手掛かりが残らない。

**原因の詳細は画面に出さない。** 利用者に打てる手が無く、
表の構造を晒すことにもなるため。

成否は**例外の有無だけ**で決める。値の中身で判断すると、
正当な空の結果（0 件・null）を失敗として扱ってしまう。

### 往復を減らした（案 C）

チャット画面の直列の取得を束ねた。

- 変更前: プロジェクト → 利用者 → 索引件数 → 予測 1 → 予測 2 を順に待つ（5 回）
- 変更後: 上記を 1 度に待ち、**利用者が決まってからでないと引けない対話履歴のみ**を後から引く

## どう確認したか

- `lib/domain/__tests__/load-result.test.ts` 7 件
  （失敗しても投げない、同期例外も捕まえる、null や 0 を成功として扱う、最初の失敗のみ返す）
- lint / typecheck / test（885 件）/ build がグリーン
- 起動してコンパイルエラーが無いことを確認

## 残っていること

キャッシュ（案 A）は次の PR で行う。
まず往復削減だけで足りるかを確かめてから、限定的に足す。
