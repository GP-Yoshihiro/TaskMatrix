# 作業ログ: PWA 対応の実機検証（2026-08-31）

## 確認できたこと

| 確認項目 | 結果 |
|---|---|
| `manifest.webmanifest` の配信 | 200 / `application/manifest+json` |
| アイコン 4 種の配信 | すべて 200 / `image/png` |
| アイコンのサイズ | 192 / 512 / 512(maskable) / 180 いずれも指定どおり |
| `head` に manifest とテーマ色 | 出力あり |
| iOS メタタグ | `apple-mobile-web-app-title` / `-status-bar-style` / `apple-touch-icon` |
| `viewport-fit=cover` | 出力あり |
| `sw.js` の配信 | 200 / `application/javascript` / リダイレクトなし |
| `/offline` の表示 | 200。認証を要求しない |

## Next.js 16 の仕様に対応した点

`appleWebApp.capable: true` を指定しても、Next.js 16 は
**標準の `mobile-web-app-capable` を出力し、`apple-mobile-web-app-capable` は出力しない**。
バンドルされたドキュメントで確認した。

古い iOS は `apple-` 接頭辞版しか解釈しないため、
`metadata.other` で併記して両方を出力するようにした。

## 検証できなかったこと

**この環境（Claude の埋め込みブラウザ）では Service Worker を登録できない。**

```
Failed to register a ServiceWorker for scope ('http://localhost:3000/')
with script ('http://localhost:3000/sw.js'):
An unknown error occurred when fetching the script.
```

切り分けた結果:

- `/sw.js` は 200 で返り、MIME も `application/javascript`、リダイレクトもない
- `isSecureContext` は true、`serviceWorker` API も `caches` API も存在する
- スクリプトの中身も 2630 文字すべて取得できている

したがってスクリプト側の問題ではなく、埋め込みブラウザ（Electron ベース）側の制約と判断した。
**実ブラウザでの登録確認はお客様にお願いする必要がある。**

## 代わりに固めた検証

計画時に「`sw.js` は `lib/domain/pwa.ts` の写しなのでずれる危険がある」と
書いていた点を、テストで固定した。

`node:vm` で `sw.js` をワーカー相当の文脈に読み込み、
内部の `chooseStrategy` と `APP_SHELL` を取り出して、
`lib/domain/pwa.ts` の実装と**全 12 ケースで一致すること**を検証している。

検証しているケース:

- POST / PUT / DELETE が素通しされる（Server Actions を壊さない）
- ページ遷移がネットワーク優先
- ビルド成果物・アイコン・manifest がキャッシュ優先
- `/api` が素通し（ページ遷移であっても）
- 別オリジン（Supabase / Gemini）が素通し
- 未知のパスが素通し
- `APP_SHELL` の内容が一致し、利用者データの経路を含まない

あわせて、`install` / `activate` / `fetch` の 3 つのイベントを登録していることと、
キャッシュ名にバージョンが付いていることも確認している。

## 学び

Service Worker のように「import できないので写しを持つ」場面では、
写しが正しいことを機械的に検証する手段を用意しないと、
片方だけ直して気づかない事故が起きる。
今回は `node:vm` で実ファイルを読み込んで突き合わせることで解決した。
