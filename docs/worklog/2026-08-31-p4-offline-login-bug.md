# 障害記録: オフライン時にログイン画面へ飛ぶ（2026-08-31）

## 症状

Wi-Fi を切って再読み込みすると、オフラインページではなく
ログイン画面が表示される。しかも接続が無いためログインもできない。

## 誤った初期判断

Service Worker の不具合だと考えたが、それは一部でしかなかった。

## 事実の切り分け

### 1. テスト手順そのものが誤っていた

**Wi-Fi を切っても `localhost:3000` は切断されない。** ループバック接続のため
同じ端末内で完結する。ブラウザから見てオフラインではないので、
Service Worker のオフライン経路はそもそも通っていなかった。

Chrome の開発者ツールの「Offline」は localhost にも効くが、
Safari には同等の機能がないため気づきにくい。

### 2. その状況で起きていた本当の問題

1. サーバー（Next.js）は届く
2. サーバーが Supabase にセッション確認を行う → Wi-Fi が無いので失敗
3. **失敗を「ログインしていない」と解釈**して `/login` へリダイレクト
4. ログイン画面でも Supabase に届かないので進めず、行き止まりになる

「到達できなかった」と「認証されていない」を区別していなかったのが原因。
本番でも Supabase が一時的に不調になれば、全利用者がログアウト扱いになる。

利用者からの指摘:
> ログイン画面の段階でインターネットの接続が確認できない時は
> 「オフラインです」と表示するように設計を見直しが必要かもしれない。

そのとおりだった。

## 対処

- `isConnectivityFailure` を追加。Supabase が到達不能なときに返す
  `AuthRetryableFetchError` / status 0 / `fetch failed` を判定する
- `decideProtectedRouteAction` を追加。保護ルートで
  「未認証」なら `/login`、「確認できなかった」なら `/offline` に振り分ける
- `proxy.ts` とルートページ（`/`）に適用
- `describeAuthFailure` でも接続失敗を最優先で分け、
  「パスワードが正しくありません」と取り違えないようにした

### 検証方法

Supabase の URL を `https://patasstmipeqaaovfihv.unreachable.invalid` に差し替えて再現した。
**プロジェクト参照（先頭のラベル）を保つのが要点。**
Cookie 名は URL から導出されるため、ホストごと変えると
「セッションが無い」状態になってしまい、目的の経路を再現できない。

結果:

| 状況 | 修正前 | 修正後 |
|---|---|---|
| 認証済み + Supabase 到達不能 + `/dashboard` | `/login` へ | **`/offline` へ** |
| 認証済み + Supabase 到達可能 + `/dashboard` | 表示 | 表示（変化なし） |
| 未認証 + Supabase 到達可能 + `/dashboard` | `/login` へ | `/login` へ（変化なし） |
| `/login` と `/offline` 自体 | 表示 | 表示（行き止まりにしない） |

## 学び

エラーを「安全側に倒して一律に扱う」と、原因の分類が潰れて
利用者が行き止まりに入る。認証まわりでは特に、
「否認された」のか「確認できなかった」のかを必ず分けること。

同じ誤りを二度繰り返した（先のログイン不能の障害でも
あらゆる失敗を「パスワードが正しくありません」に丸めていた）。
