# 招待コード操作時のパスワード再確認

ブランチ: `feature/invitation-copy`（コピー機能に続けて実装）

## 何を

招待コードの一覧は今までどおり閲覧できるが、次の操作の前にパスワードを求める。

- 新規コードの発行
- 発行直後のコピー
- 一覧のコードのコピー
- 一覧の行を押して詳細を開く

一度確認すれば 15 分間は続けて操作できる。

## なぜ

ログイン済みであることと、**今その人が操作していること**は別物である。
席を離れた間に画面が開いたままなら、招待コードの発行も閲覧もできてしまう。

## 設計の要点

### 画面で伏せるだけでは意味がない

当初「コードは今までどおりページに載せ、画面側で伏せる」形を考えたが、これは
見せかけにしかならない。**伏せていても、コードはすでに手元に届いている**（ページの
データに含まれている）ため、開発者ツールで読めてしまう。

そのため次のようにした。

- ページの初期表示には**コードの全文を含めない**（`toSummaries` で暗号文を落とす）
- パスワードの確認後に、専用の Server Action で改めて読み出す

### サーバー側で必ず確かめる

画面側の施錠は操作の入口を揃えるためのもので、守っているのはサーバー側。
`requireAdmin` を「管理者であること」から
「**管理者であり、かつ直前にパスワードを確認済みであること**」に強めた。
この関数を通らない経路から直接呼ばれても、行為そのものが拒否される。

### 確認済みの印

Cookie に持たせるが、**中身は暗号化**して利用者 ID と期限を封じた（AES-256-GCM）。
平文の印を置くと、値を作れば誰でも確認済みを名乗れてしまう。
利用者 ID を照合しているため、取り違えで他人の確認済み状態を借りることもできない。

Cookie は `httpOnly` / `sameSite=strict` / 本番では `secure`、`/settings` 配下に限定。

### 確認は使い捨てのクライアントで行う

今のセッションでログインし直すと、確認しただけのつもりが token を入れ替えてしまう。
`persistSession: false` の別クライアントで照合し、セッションには触れない。

### 一覧の項目は明示的に並べる

除外する形（`...rest`）で書くと、あとで表に列が増えたとき、
気付かないまま画面へ流れてしまう。残す項目を列挙する形にした。

## 割り切り

- 確認の有効時間は 15 分。席を離れる程度の間で切れる長さにした
- 発行は、確認のあと自動では続けない。押した意図の確認から時間が空くため、
  改めてボタンを押してもらう
- コピーも確認後に押し直しになる。クリップボードへの書き込みは、
  利用者の操作から直接でないとブラウザが拒否するため
