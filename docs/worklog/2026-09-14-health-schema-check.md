# 表の構造を /api/health で確かめられるようにする

ブランチ: `feature/health-schema-check`

## なぜ

移行 SQL の適用漏れが **2 度**起きた（`0017` と `0018`）。
いずれも「適用した」あとで実際には列が無く、タスク画面と予定画面が使えなくなった。

**アプリの外から確かめる手段が無かった**ため、毎回やり取りを重ねて
切り分けることになっていた。開発側から DB を照会できない制約もある。

## 何を

`/api/health` に、期待する表と列がそろっているかの確認を足した。

```
{"ok":true, ..., "schema":{"ok":true,"missing":[]}}
```

不足があれば、列名を添えて返す。

```
{"ok":false, ..., "schema":{"ok":false,"missing":["tasks.estimated_days"]}}
```

## 何を返さないか

**データの中身は一切返さない。**

- 問い合わせは `limit(0)`。**行は 1 件も返らない**
- 返すのは列の名前と有無だけ

## 設計の判断

### 「調べられなかった」を「問題なし」と見せない

サービス用の鍵が無い、あるいは確認そのものが失敗した場合は
`ok: null` と注記を返す。**未確認を成功と取り違えると、
この仕組みを入れた意味が無くなる。**

### 全列ではなく、あとから足した列を並べる

適用漏れが起きるのは追加分であり、全列を書くと更新が追いつかない。

### 構造の確認が失敗しても、設定の確認は返す

切り分けの手段を、別の不具合で失わないため。

### 不足があれば HTTP も 503 にする

本文を読まなくても、状態の異常が分かる。

## どう確認したか

- `lib/domain/__tests__/schema-check.test.ts` 9 件
  （期待する列の一覧、エラー文からの抽出、結合の判定、原因不明の扱い）
- **実際に起動して確認した**
  - 現状: `schema: {"ok": true, "missing": []}`（0017・0018 の適用も確認できた）
  - **わざと存在しない列を加えたところ**、
    `{"ok": false, "missing": ["project_members.not_a_real_column"]}` と
    HTTP 503 を返した。検出できることを実証した
- lint / typecheck / test（934 件）/ build がグリーン
