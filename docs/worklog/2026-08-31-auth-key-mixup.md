# 障害記録: ログイン不能（2026-08-31）

## 症状

既存アカウントでログインできず、同じメールアドレスでの新規登録もできない。
画面には「メールアドレスまたはパスワードが正しくありません。」と表示された。

## 誤った初期判断

セッションの有効期限切れだと考えたが、これは誤りだった。
`auth.users` を確認したところアカウントは完全に正常で
（パスワードあり・確認済み・BAN なし・削除なし）、期限切れでは説明がつかなかった。

## 実際の原因

`.env.local` の `NEXT_PUBLIC_SUPABASE_ANON_KEY` が **Gemini API キーで上書きされていた**。
Gemini のキーを追記する際に Supabase の公開キーの行を書き換えてしまったと考えられる。

その結果、Supabase の認証エンドポイントが `Invalid API key`（HTTP 401）を返し、
ログインもサインアップも認証以前の段階で失敗していた。
同じアドレスで新規登録できなかったのは、既に登録済みだったためで正常な挙動。

## どう切り分けたか

わざと誤ったパスワードで `/auth/v1/token` を直接叩き、返るエラーを見た。

- 修正前: `{"message": "Invalid API key"}` (401) → キーの問題
- 修正後: `{"error_code": "invalid_credentials"}` (400) → パスワード照合まで到達

利用者のパスワードを扱わずに原因を特定できる方法として有効だった。

## 対処

1. Supabase から正しい公開キーを取得し `.env.local` を再構成。
   取り違え防止のコメントを各行に追加した。
2. **原因が隠れていた実装上の欠陥を修正した。**
   `signInAction` があらゆる失敗を「パスワードが正しくありません」に丸めていたため、
   設定ミスが資格情報の誤りに見えていた。`describeAuthFailure` を追加し、
   設定ミス・サービス障害・レート制限・メール未確認・資格情報の誤りを区別するようにした。

## 教訓

利用者に見せるエラーメッセージを一律に丸めると、障害の切り分けができなくなる。
「安全側に倒して詳細を出さない」ことと「原因の分類を潰す」ことは別問題である。
分類は残したうえで、表示する文言を状況ごとに変えるべきだった。
