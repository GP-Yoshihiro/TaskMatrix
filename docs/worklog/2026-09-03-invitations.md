# 招待コードによる登録制限

ブランチ: `feature/invitations`
設計・計画: `docs/plans/2026-09-03-invitations.md`

## 何を

URL を知っていれば誰でも登録できる状態をやめ、
管理者が発行した招待コードを持つ人だけが登録できるようにした。

## なぜ

費用。Gemini API のキーはサーバー側の 1 本を全員で共有しており、
登録者の AI 利用がそのまま運用者の請求になる。利用回数の上限も無い。

## どう作ったか

### 照合だけでは制限にならない

当初「`signUpAction` の中でコードを照合する」形を考えたが、これは機能しない。
ブラウザ用のキー（`NEXT_PUBLIC_SUPABASE_ANON_KEY`）は仕様上クライアントに
埋め込まれており、そのキーで Supabase の登録エンドポイントを直接叩けば
画面を通さず登録できてしまう。

そのため次の 2 つを揃える構成にした。

1. Supabase 側の公開サインアップを無効化する（運用者の操作）
2. アカウント作成はサーバー専用キーで行い、照合を通った場合のみ実行する

管理 API は公開サインアップの設定に縛られないため、この経路だけが残る。

### 「確保してから作る」順にした理由

先に照合してから作る順だと、その隙間に同じコードで二重に通る。
`update ... where used_at is null and revoked_at is null and expires_at > now`
の 1 文で原子的に確保し、0 行なら拒否する。
アカウント作成に失敗したら確保を戻し、使われていないコードを潰さない。

### 平文を保存しない

`api_tokens` と同じ流儀。DB が読まれてもコードとして使えないようにする。
代償として発行後に読み返せないため、紛失時は無効化して再発行する。

### 失敗理由を細かく返さない

「使用済み」と「存在しない」を区別して返すと、総当たりの手掛かりになる。
どちらも同じ文言で返している。

## 割り切り

- **メールアドレスの実在確認は行わない。** 管理 API で作るため確認メールを
  経由しない。招待コードで人を絞る前提での割り切り
- 発行画面は管理者以外には 404 を返す。403 だと画面の存在だけは伝わるため
