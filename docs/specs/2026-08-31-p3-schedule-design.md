## 1. 目的とスコープ

P2 で作られたタスクに対し、AI が実行日時を算出して提案し、
ユーザーが確定したものをカレンダーに反映する。

### 対象とするもの

- 稼働日・稼働時間帯を考慮した AI によるスケジュール算出
- **算出理由の明記**（なぜその日時に割り当てたか）
- 仮案プレビュー → **ユーザーによる日時の編集** → 「確定」でカレンダーへ反映
- **重複の検出と明示**、確定時の警告ダイアログ
- 自前実装の月間カレンダービュー
- Apple カレンダー等に取り込める **.ics 書き出し**
- 稼働条件（稼働曜日・時間帯・1日の上限時間）の設定画面

### 対象としないもの

Google Calendar API による双方向同期（P4 へ）、
.ics のインポート、重複の自動回避（意図的に行わない。§2 参照）、
複数人でのリソース調整、繰り返し予定。

## 2. 確定した仕様判断

| 論点 | 確定 | 理由 |
|---|---|---|
| カレンダー連携 | **.ics 書き出しのみ**。Google Calendar は P4 | OAuth 設定が利用者側の作業を要するため、まず外部設定なしで使える形にする |
| 算出条件 | **稼働日・稼働時間帯を考慮**。所要時間も AI に推定させる | 期限と優先度だけでは実行可能な計画にならない |
| カレンダー UI | **自前の月間ビュー** | 依存を増やさず、デザイントークンとプラットフォームテーマに追従できる |
| 確定前の保存 | **しない**（P2 と同じ非破壊方針） | 仮案を勝手に保存すると既存の確定予定を壊しかねない |
| 重複の扱い | **重複を許して仮反映し、箇所ごとに明示。確定時に警告する** | タスクの重さによって許容できる重複は変わるため、機械的に排除せず利用者に判断させる |
| 仮案の編集 | **確定前にユーザーが日時を編集できる** | AI の案をそのまま受け入れるか捨てるかの二択では実用にならない |

### 重複についての方針

**重複を自動で回避しない。** タスクの重さによって許容できる重複は変わるため、
機械的に別日へ追い出すと不自然な計画になる。代わりに次のようにする。

1. AI は各タスクの**重さ**（優先度と推定作業工数から算出）を返し、
   既存の確定済みスケジュールと重ねてよいかを判断したうえで日時を提案する
2. サーバーは AI の判断とは独立に、**重複を機械的に検出する**
   （仮案どうし、および仮案と確定済みの両方）
3. 画面では重複している箇所を**予定ごとに明示**する
   （「〇〇 と重複しています」）
4. 確定時に重複が残っていれば**警告ダイアログ**を出し、
   了承があればそのまま確定する

重複の検出は決定的な処理としてサーバー側で行い、AI の判断は
「重ねてよいか」の助言として併記するに留める。AI の判断だけに頼らない。

## 3. データモデル

```
schedules
  id          uuid PK
  project_id  uuid not null -> projects(id) ON DELETE CASCADE
  task_id     uuid not null -> tasks(id)    ON DELETE CASCADE
  starts_at   timestamptz not null
  ends_at     timestamptz not null
  reason      text not null default ''   -- AI による算出理由
  created_by  uuid not null -> profiles(id)
  created_at  timestamptz
  updated_at  timestamptz

work_settings          -- 利用者ごとの稼働条件。1 ユーザー 1 行
  user_id        uuid PK -> profiles(id) ON DELETE CASCADE
  work_days      smallint[] not null default '{1,2,3,4,5}'  -- 0=日 〜 6=土
  work_start     time not null default '09:00'
  work_end       time not null default '18:00'
  daily_capacity_minutes integer not null default 360        -- 1 日に割り当てる上限
  timezone       text not null default 'Asia/Tokyo'
  updated_at     timestamptz
```

`schedules` は**確定済みのものだけ**を保持する。仮案は画面上の状態としてのみ存在する。

`task_id` を `ON DELETE CASCADE` にする理由は、タスクが消えた予定を残しても
意味を持たないため。`tasks` 側の削除ダイアログにその旨を明記する。

RLS は P1・P2 と同じく `projects.owner_id = auth.uid()` を起点とする。
`work_settings` は `user_id = auth.uid()`。

## 4. R-21 に基づく外部送信の内容

| 項目 | 内容 |
|---|---|
| **何を** | 未完了タスクの一覧（タスク名・説明・優先度・期限）、稼働条件、今日の日付、**確定済みスケジュールの日時とタスク名** |
| **どこへ** | Google Gemini API（Interactions API） |
| **なぜ** | 実行日時と所要時間を算出し、その理由を生成するため |
| **どうなるか** | 有料 API 経由では学習に使用されない方針。無料枠では学習に利用される場合がある |

確定済みスケジュールを送るのは、AI が既存の予定と重ねてよいかを
タスクの重さから判断するために必要なためである。

### 送信しないもの

ファイルの本文、ファイル名、プロジェクト名、フォルダ名、
ユーザーのメールアドレスや ID、Supabase のキー類、
タスクの不透明点メモと AI 改善提案（日程算出に不要なため）。

## 5. アーキテクチャ

P1・P2 の方針を継承する。読み取りは Server Components、書き込みは Server Actions。
Gemini への依存は `lib/gemini` に閉じ込め、`lib/usecases` はインターフェース越しに呼ぶ。

**例外として `.ics` の書き出しのみ Route Handler を使う。**
ファイルダウンロードには `Content-Disposition` ヘッダーが必要で、
Server Action では扱えないため。P1 設計書 §5.1 で「必要になった時点で
Route Handlers を追加する」と決めていた通りの追加である。


## 6. 全体の流れ

第1〜3フェーズを通したユーザーの体験は次のようになる。

```
ドキュメントを登録
  → AI がタスクを抽出（P2）
  → タスクとして登録
  → カレンダーに仮反映（プレビュー）   ← 本フェーズ
  → ユーザーが日時を編集
  → 確定
  → 本カレンダーに反映
```

## 6.1 算出フロー

```
1. カレンダー画面で「スケジュールを算出」を押す
2. 送信内容の確認ダイアログを表示（R-21）
3. 次を Gemini に送る
     - 未完了タスク（status <> 'done'）の名称・説明・優先度・期限
     - 稼働条件（稼働曜日・時間帯・1日の上限）
     - 今日の日付
     - 確定済みスケジュールの日時とタスク名
4. 構造化出力で 開始日時・終了日時・算出理由・重さ・重複の可否 を受け取る
5. サーバー側で検証する
     - 日時として解釈できるか
     - 稼働日・稼働時間帯の範囲内か（外れたものは補正、補正できなければ除外）
6. サーバー側で重複を機械的に検出する
     - 仮案どうしの重複
     - 仮案と確定済みスケジュールの重複
7. 【仮案】としてカレンダー上に確定済みと区別して表示（この時点では保存しない）
     - 重複している予定には、どれと重複しているかを明示する
     - AI が返した重さと「重ねてよいか」の判断を併記する
8. ユーザーが日時を編集できる（編集のたびに重複を再検出して表示を更新する）
9. ユーザーがチェックを付けて「確定」
10. 選択したものに重複が残っていれば【警告ダイアログ】を表示する
      - 重複している組み合わせを一覧で示す
      - 「重複を承知で確定する」を選べばそのまま保存する
11. 選択されたものだけを schedules に保存
```

AI の出力を鵜呑みにせず、**稼働条件の範囲内かをサーバー側で必ず検証する**。
P2 で AI が `due_date` に自然言語を返した実績があるため、日時も同様に信用しない。
**重複の検出も AI に任せず、サーバー側で決定的に行う。**

## 6.2 タスクの「重さ」

AI に優先度と推定作業工数から重さを判定させ、既存予定と重ねてよいかの
判断材料にする。判定結果は仮案の各予定に併記し、利用者の判断を助ける。

| 重さ | 目安 | 重複の扱い |
|---|---|---|
| `heavy` | 優先度が高く、まとまった作業時間を要する | 重ねるべきでない |
| `normal` | 標準的なタスク | できれば重ねない |
| `light` | 短時間で終わる、優先度が低い | 重なっても差し支えないことが多い |

**この判定はあくまで助言である。** 重複を機械的に排除する根拠には使わない。
最終的に重複を許すかどうかは、警告ダイアログを見た利用者が決める。

## 6.3 Gemini への出力スキーマ

```
{
  schedules: [
    {
      task_title: string           // どのタスクに対する提案か（照合用）
      starts_at: string            // ISO 8601（例 2026-09-01T09:00:00+09:00）
      ends_at: string              // ISO 8601
      reason: string               // なぜその日時にしたか。日本語
      weight: 'heavy'|'normal'|'light'   // 優先度と作業工数から判定した重さ
      overlap_acceptable: boolean  // 既存予定と重なっても差し支えないか
    }
  ],
  overall_note: string             // 全体方針の説明。1〜3文
}
```

## 6.4 重複検出のロジック

`lib/domain/schedule.ts` に純粋関数として実装し、単体テストの中心とする。

- 2 つの期間が重なるとは `aStart < bEnd && bStart < aEnd` が成り立つこと
  （終了時刻と開始時刻が同一の「隣接」は重複としない）
- 検出対象は次の 2 通り
  1. 仮案どうし
  2. 仮案と確定済みスケジュール
- 各仮案に対し、重複している相手の一覧を返す
- ユーザーが日時を編集したら再検出する

## 7. .ics 書き出し

RFC 5545 に沿った最小構成を自前で組み立てる（ライブラリを増やさない）。

```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//TaskMatrix//JA
CALSCALE:GREGORIAN
BEGIN:VEVENT
UID:<schedule id>@taskmatrix
DTSTAMP:<生成時刻 UTC>
DTSTART:<開始 UTC>
DTEND:<終了 UTC>
SUMMARY:<タスク名>
DESCRIPTION:<算出理由>
END:VEVENT
END:VCALENDAR
```

注意点:

- 日時は **UTC の `YYYYMMDDTHHMMSSZ` 形式**で書く
- 1 行は 75 オクテット以内に折り返す（超える行は次行を空白で開始する）
- `SUMMARY` と `DESCRIPTION` の `\` `;` `,` と改行をエスケープする
- 改行コードは **CRLF**

## 8. エラー処理

追加するエラーコード:

| コード | 発生条件 | 表示メッセージ |
|---|---|---|
| `NO_SCHEDULABLE_TASKS` | 未完了タスクが 0 件 | 予定を立てるタスクがありません。 |
| `INVALID_SCHEDULE_RANGE` | AI の日時が解釈できない・稼働条件から大きく外れる | 算出結果を解釈できませんでした。もう一度お試しください。 |

既存の `AI_*` 系のコードは P2 のものをそのまま使う。

## 9. テストと検証

- **単体**: `lib/domain/schedule.ts`（稼働日判定・範囲検証・**重複検出**・重さの表示名）、
  `lib/domain/ics.ts`（エスケープ・行折り返し・UTC 変換）、
  `lib/domain/calendar.ts`（月間グリッド）
- **ユースケース**: Gemini をモックした `planSchedule`。**実 API は呼ばない**
- **実機**: 開発サーバーで次を通しで確認する
  1. 算出 → 仮案がカレンダーに表示される
  2. 重複している予定に「〇〇 と重複しています」が出る
  3. 日時を編集すると重複表示が更新される
  4. 重複を残したまま確定しようとすると警告ダイアログが出る
  5. 了承すると保存され、取り消すと保存されない
  6. .ics を書き出し、実際に Apple カレンダーで開ける

## 12. P3 の完了条件

1. 稼働条件（曜日・時間帯・1日の上限）を設定でき、保存される
2. 未完了タスクからスケジュール仮案を算出できる
3. 各提案に**算出理由**が日本語で表示される
4. 各提案に**重さ**と「重ねてよいか」の判断が表示される
5. 稼働日・稼働時間帯から外れた提案が補正または除外される
6. 仮案と確定済みがカレンダー上で区別して表示される
7. **重複している予定に、どれと重複しているかが箇所ごとに表示される**
8. **仮案の日時を編集でき、編集すると重複表示が更新される**
9. **重複を残したまま確定しようとすると警告ダイアログが出る**
10. **警告を了承すれば保存され、取り消せば保存されない**
11. チェックしたものだけが確定・保存される
12. 確定前の状態では `schedules` に保存されない
13. 月間カレンダーで前後の月に移動できる
14. .ics を書き出せ、Apple カレンダーで開ける
15. タスクが 0 件のときに日本語メッセージが出る
16. 他ユーザーのスケジュールにアクセスできない
17. `lint` / `typecheck` / `test` / `build` がすべてグリーン
