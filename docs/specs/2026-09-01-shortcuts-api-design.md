# iOS ショートカット / Webhook API 設計書

作成日: 2026-09-01

## 目的

iPhone のショートカットや Siri から TaskMatrix を使えるようにする。
思いついたときにタスクを入れ、朝に今日やることを確認する、という使い方を想定する。

## 前提となる制約

ショートカットは **Cookie を持てない**。
既存の画面と `.ics` 出力はブラウザのセッション（Cookie）で認証しており、
その上で Supabase の RLS が「自分の行しか触れない」ことを保証していた。

トークン認証ではセッションが無く、**RLS の安全網が外れる**。
サーバー専用キー（Service Role Key）で接続するため、RLS は適用されない。
この設計の中心は、その安全網を別の形で作り直すことにある。

## 中心となる安全策：操作対象をリクエストから受け取らない

**リクエスト本文に `projectId` を受け取らない。**

- トークンを引くと、そのトークンに紐づく `project_id` と `user_id` が決まる
- すべての問い合わせを、その `project_id` で明示的に絞る

こうすると「別プロジェクトの ID を指定して覗く」攻撃が**原理的に成立しない**。
指定する場所そのものが無いためである。

チェックを書き忘れる余地を残さないことが要点で、
「毎回検証する」という規律に頼る設計にはしない。

## トークン

### 形式

```
tmx_<base64url 43 文字>
```

`crypto.randomBytes(32)` を base64url で表現する。

### 保存

**SHA-256 のハッシュだけを保存する。** 平文は保存しない。

平文で持つと、データベースが読まれた時点でトークンがそのまま使える。
ハッシュなら読まれても使えない。

発行直後の 1 回だけ画面に全文を表示し、以降は再表示できない。
一覧には識別用に接頭辞（`tmx_a1b2c3d4…`）だけを出す。

### 照合

提示されたトークンをハッシュ化し、`token_hash` の等値検索で引く。
索引が効く 1 回の問い合わせで済み、総当たりの比較を行わない。

### 失効

行を削除する。削除後はそのトークンで一切の操作ができない。

## テーブル `api_tokens`

| 列 | 意味 |
|----|------|
| `project_id` | このトークンが操作できる唯一のプロジェクト |
| `user_id` | 作成者。タスクの `created_by` に入れる |
| `name` | 用途がわかる名前（「iPhone のショートカット」など） |
| `token_hash` | SHA-256（unique） |
| `display_prefix` | 一覧表示用の接頭辞 |
| `last_used_at` | 最終利用日時。使われていないトークンを見つけるため |
| `rate_window_started_at` / `rate_count` | 回数制限の状態 |

RLS: 自分が所有するプロジェクトのトークンのみ操作できる。
API 側はサーバー専用キーで接続するため RLS を通らない。
そのため上記の「操作対象を受け取らない」構造が要になる。

## エンドポイント

認証は `Authorization: Bearer tmx_...` とする。

### `POST /api/v1/tasks`

タスクを追加する。

```json
{ "title": "資料を作る", "description": "", "priority": "medium",
  "dueDate": "2026-09-05", "assignee": "" }
```

`title` のみ必須。応答:

```json
{ "id": "...", "title": "資料を作る", "message": "「資料を作る」を追加しました。" }
```

`message` は日本語の 1 行。**ショートカットでそのまま読み上げに使える**ようにする。

### `GET /api/v1/tasks/today`

今日やることを返す。

```json
{ "date": "2026-09-01", "count": 3,
  "summary": "今日のタスクは 3 件です。",
  "tasks": [ { "id": "...", "title": "...", "priority": "high",
              "dueDate": "2026-09-01", "startsAt": "...", "endsAt": "..." } ] }
```

**「今日やること」の定義**（未完了のタスクのうち、次のいずれか）:

1. 期限が**今日以前**のもの（超過分を含む）
2. **今日の確定済み予定**に紐づくもの

期限だけで絞ると、期限が先でも今日に予定を入れたタスクが漏れる。
予定だけで絞ると、予定を立てていない期限切れのタスクが漏れる。
どちらも「今日やること」としては欠けるため、和集合とする。

並び順は、今日の予定があるものを開始時刻順に先に出し、
続けて期限の近い順、同じなら優先度の高い順とする。

## 回数制限

トークン 1 本あたり**毎分 60 回**。超えたら `429` と `Retry-After` を返す。

専用の記録表は作らない。トークン行に「窓の開始時刻」と「回数」を持たせ、
1 回の更新で判定する。Redis のような追加基盤を持ち込まずに済む。

窓は固定窓とする。厳密な移動窓ではないが、
個人利用の誤操作・暴走を止めるには十分であり、実装と状態が単純になる。

## 応答の方針

| 状況 | 応答 |
|------|------|
| ヘッダーが無い / 形式が違う / 該当なし | `401` |
| 回数超過 | `429` + `Retry-After` |
| 入力が不正 | `400` |
| 設定不備（サーバー専用キーが無い） | `503` |

**認証失敗の理由を書き分けない。**
「そのトークンは存在するが失効済み」と返すと、有効なトークンの探索を助けてしまう。

トークンそのものは、ログにも応答にも出さない。

## 画面

プロジェクト画面に「連携トークン」を追加する。

- 発行（名前を付ける）→ **発行直後だけ全文を表示**
- 一覧（名前・接頭辞・最終利用日時・発行日）
- 失効（確認ダイアログ。「一度失効すると元に戻せません」を明記）
- ショートカットに貼り付ける URL の表示

## 実装しないもの

- **タスクの削除・更新** — 追加と読み取りのみ。漏れても既存データを壊せない
- **AI 抽出の API 起動** — トークンが漏れると第三者が Gemini の枠を消費できてしまう
- OAuth — トークンで足りる
- 移動窓の厳密な回数制限

## 運用上の必要事項

`SUPABASE_SERVICE_ROLE_KEY` を `.env.local` に設定する必要がある。
**未設定の場合、API は `503` を返し、画面にもその旨を表示する**（黙って失敗させない）。
このキーはサーバー専用であり、クライアントへ露出させない（R-14）。
