# 変更履歴機能 設計書

作成日: 2026-09-02
（2026-09-02 ユーザーとのインタビューにより要件確定）

## 目的

管理職の方がプロジェクト全体の動きを把握でき、編集者は自分のファイルの経緯を追えるようにする。

このアプリは管理職のプロジェクト管理の負荷軽減を目的としている。
「誰がいつ何を変えたか」を一覧で追えることが、この機能の中心的な価値になる。

## 既存実装との関係

現在は `file_versions` に**版ごとの全文**を保存し、
ファイル別の「変更履歴」画面で差分を表示している。

この設計では次のように変える。

| | 現在 | 変更後 |
|---|------|--------|
| 置き場所 | `file_versions`（ファイルに従属） | **履歴専用の表**（ファイルから独立） |
| 保存内容 | 版ごとの全文 | **変更箇所だけ** |
| ファイル削除時 | 履歴も消える | **履歴は残る** |
| 閲覧画面 | ファイル別 | **プロジェクト全体**（ファイル別は廃止） |

### 過去版の全文を捨てる判断

現在の履歴画面は**差分を見せるだけ**で、過去の版をダウンロードする機能も
巻き戻す機能も無い。したがって全文を捨てても**利用者から見て失われる機能は無い**。

バイナリ（Excel / Word / PDF）は版ごとにストレージへ実体を置いているが、
過去版を見る手段が無いため、これも破棄する。置いたままでは容量だけを消費する。

なお、差分を最新版から逆にたどれば過去の全文は再現できる。
必要になった時点で実装できるため、情報として失われるわけではない。

## データ設計

### `history_entries`（新設）

| 列 | 意味 |
|----|------|
| `project_id` | 所属プロジェクト |
| `file_id` | 対象ファイル。**外部キーを張らない**（ファイルを消しても履歴を残すため） |
| `file_name` / `file_extension` / `file_kind` | 記録時点の値を焼き込む。ファイルが消えても表示できる |
| `action` | `created` / `updated` / `deleted` |
| `version` | 対応する版番号（あれば） |
| `changes` | 変更箇所（行の追加・削除）。全文は持たない |
| `added_count` / `removed_count` | 追加・削除された行数。一覧の要約に使う |
| `truncated` | 変更が多すぎて一部しか保存していないか |
| `author_id` | 変更者。アカウント削除時は null |
| `author_name` | 記録時点の表示名。**アカウントが消えても誰の操作か残す** |
| `created_at` | |

`author_id` が生きていれば `profiles` の現在の表示名を優先し、
無ければ `author_name` を使う。改名が過去の履歴にも反映され、
かつ退会後も「誰か分からない」状態にならない。

### 変更箇所の持ち方

```json
[{ "type": "added", "line": 12, "text": "..." },
 { "type": "removed", "line": 11, "text": "..." }]
```

行番号のズレは厳密に合わせない（ユーザー了承済み）。
追加は変更後の本文での行番号、削除は変更前の本文での行番号を持つ。

**保存する行数に上限を設ける。** 巨大なファイルを丸ごと書き換えると
変更行が数万件になり、1 件の履歴で容量を食い尽くすため。
上限を超えたときは先頭から一定数だけ保存し、`truncated` を立てる。
`added_count` / `removed_count` は**打ち切らず正確な値**を入れる。

### `profiles` への追加

`display_name` を追加する。設定画面で登録し、履歴の変更者名に使う。
未登録のときはメールアドレスの `@` より前を使う。

## 保存期間

**半永久**。期限では消さない。

データベースの容量が閾値に達したときだけ、
**ロックタグが付いたファイルの履歴を除いて**、古い順に削除する（第 3 期）。

## 履歴ページ

`/projects/[projectId]/history`

### 一覧

1 項目 1 行で、次を並べる。

| 位置 | 内容 | 省略 |
|------|------|------|
| ① | ファイル形式ごとの色の丸 | 不可 |
| ② | 日付（2026/09/02） | 不可 |
| ③ | ファイル名.形式 | 可 |
| ④ | 変更項目（追加 / 編集 / 削除） | 不可 |
| ⑤ | 変更者名 | 可 |

**1 行に収まらない場合は、省略可能項目を短縮して 1 行に収める。**
行の高さが揃っていないと、量が多いときに一覧として読めないため。

- 既定は新しい順。昇順・降順を切り替えられる
- **無限スクロール**でプロジェクト始動時まで遡れる
- 「編集」には下線を引き、クリックできるようにする

### 差分の表示（第 2 期）

「編集」をクリックすると、**ページを切り替えず画面右側**に変更箇所を表示する。
履歴側は左に圧縮される。境界をドラッグして比率を変えられ、
**変えた比率は記憶して以降も適用する**。既定は中央で分割。

### 検索（第 2 期・第 3 期）

ファイル名・ファイル形式・年月・日付範囲（第 2 期）、タグ（第 3 期）。

### ファイルから履歴へ

編集中のファイルに履歴ボタンを置き、押すと履歴ページへ移動する。
その際**ファイル名で検索した状態**にする。

既存のファイル別履歴画面（`/files/[fileId]/history`）は**廃止**する。
同じ役割を 2 箇所に持つと、どちらを見ればよいか分からなくなるため。

## タグ（第 3 期）

- **ファイルごと**に付与する
- 付与できる場面: アップロード時・保存時・履歴ページから
- 既存タグの選択と新規作成の両方
- **ロックタグ**: 付いたファイルは削除できない。かつ容量削減の対象外

## 性能

**データベースは 1 つのままとする。**

データベースは Supabase のサーバー上で動くため、利用者の PC には負荷がかからない。
PC 側で重くなるのは一度に大量の行を描くときだけで、これは DB を分けても解決しない。

対策は次のとおり。

- `(project_id, created_at desc)` の索引で、新しい順の取得を速くする
- 一覧は一定件数ずつ読む（無限スクロール）
- **差分は保存時に計算して持つ**。一覧のたびに全文を比較しない

Supabase は 1 プロジェクト 1 PostgreSQL であり、DB を分けるには別プロジェクトが必要になる。
その場合は有料化し、**ファイル名やタグでの絞り込みができなくなる**（表をまたげないため）。
数十万件規模までは 1 つで足りる。

## バイナリファイルの扱い

Excel / Word / PDF は本文を抽出してテキストとして差分を出す
（AI 抽出で使っている仕組みを流用する）。
**書式や図の変更は見えない。** この点は画面に明記する。

## 実装しないもの

- 巻き戻し（版の復元）
- 過去版のダウンロード
- 書式・図の差分

## 3 期に分けて実装する

| 期 | 内容 |
|----|------|
| ① | 履歴の記録・一覧ページ・無限スクロール・並び替え・既存データの移行・表示名の登録 |
| ② | 分割表示の差分（ドラッグ調整・比率記憶）・検索（ファイル名／形式／年月／日付） |
| ③ | タグ・ロック・タグ検索・容量監視と自動削除 |
